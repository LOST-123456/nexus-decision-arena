## 核心结论

取消原本只是 `UPDATE agent_runs SET status='cancelled'` —— 没有任何东西告诉执行器停手，也没有任何东西阻止它之后继续写。`cancelRun` 那句「a cancelled run is provably result-free」的注释，被源码直接证伪。现在拆成两层：

| 层 | 机制 | 跨实例 |
|---|---|---|
| 数据库（权威） | `writeWhileRunActive` 在与产物写入**同一事务**内 `SELECT status … FOR SHARE`；`cancelAgentRun` 的 UPDATE 需排他锁 | ✅ |
| 执行器（加速） | `RunCancellationRegistry` 一 run 一 `AbortController`，信号贯通到 `fetch` | ❌ 刻意不跨 |

行锁把「查状态」和「写产物」压成同一个原子决定，只剩两种合法顺序：取消先提交 → 写入被拒返回 `false`；写入先提交 → 取消等待。**`false` 不是错误，是答案**——它抛 `CrossExaminationHaltedError`，引擎跳过该 run 且**不 emit `CHALLENGE_FAILED`**（主动停止 ≠ 失败）。

三条事件语义严格分开：`CANCEL_REQUESTED`（请求已落库，不含「已停止」）→ `CANCELLED`（裁决，唯一终态依据）→ `EXECUTION_STOPPED`（**只有执行器自己能写**）。

新的权威层是 `startRetryGeneration` 的**单事务**：锁链根 `FOR UPDATE` → 读全链最深 attempt → 拒绝「链已推进」和「超上限」→ 带 lineage 批量插入。事务在第一个 Provider 调用之前结束。预算来自全链而非屏幕上那一行，并存兄弟 run 无法再摊薄成本。迁移 `0020` 用复合外键 `(parent_run_id, session_id) → (id, session_id)` 让跨会话父引用**在存储层不可能**。
