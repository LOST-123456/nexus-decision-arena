Executive Summary

作品摘要

Nexus Decision Arena 不是通用 Agent 工作流编辑器，而是一个受约束的高价值决策评审引擎。 它围绕“独立分析 → 交叉质询 → 冲突检测 → 人工裁决 → 可回放报告”建立闭环。

问题

普通多 Agent 系统常把不同角色的自由文本回答并排展示，缺少可比较的断言、定向质询、未解决分歧的 结构化记录和结论变化的证据链。评委或使用者只能看到“很多观点”，无法快速判断哪些结论值得相信。

方案

系统把 Agent 输出约束为 Claim、Evidence、Challenge、Conflict 等结构化领域对象。Planner、 质询分配、状态迁移和冲突规则由确定性代码执行；LLM 只在受控边界内生成领域对象和语义判断。

01 · PRODUCT DEFINITION

问题与作品定义

1.1 真正待解决的问题

决策评审的困难不等于“缺少观点”，而在于观点之间缺少可核验的比较关系。一个可用的 AI 评审系统必须能够回答：

结论层

  • 当前建议是什么？
  • 结论是否发生变化？
  • 变化由谁触发？

证据层

  • 关键断言有何证据？
  • 哪些内容只是假设？
  • 证据是否过期或未核验？

分歧层

  • 谁不同意，具体质疑什么？
  • 质疑是否已经回应？
  • 冲突的严重度与影响范围？

裁决层

  • 人类在哪一步介入？
  • 采纳或拒绝的依据是什么？
  • 能否回放到关键事件？

1.2 产品定义

Nexus Decision Arena：面向真实决策评审的受约束多 Agent 系统。五个 AI 角色先独立分析， 再针对关键 Claim 进行交叉质询；系统把未解决分歧结构化为 Conflict，并交给人类裁决，最终输出可追溯、 可回放、可复现的决策报告。

1.3 与通用 Agent 工作流的差异

维度常见多 Agent 展示Nexus 的约束
核心对象节点、边、自由文本消息Claim、Evidence、Challenge、Conflict
观点关系并列展示，依赖阅读者归纳结构化关系与定向质询
流程控制节点自由拼装固定状态机和确定性规则
结论产生模型直接输出最终答案系统建议，人类最终裁决
可复现单位代码或一次输出完整决策过程链

1.4 明确不做

首版不实现通用工作流画布、不开放无限节点编排、不自动完成高风险决策、不把业务规则写入 UI， 也不要求真实模型 API 才能运行固定 Demo。产品边界由设计冻结规格和测试共同约束。

02 · DECISION MODEL

五角色决策模型

系统保留五个一级 Agent，避免角色膨胀和概念堆叠。数据分析、运营、合规、伦理和逻辑分析作为角色内部 Lens 存在；运行、状态展示和推理记录仍以五个一级角色为单位。

市场分析师市场趋势、用户需求、规模口径、数据可信度与获客路径。
技术专家架构可行性、实现路径、工程量、依赖条件与部署风险。
财务分析师成本、收入、现金流、单位经济与运营效率。
风险审查员合规、隐私、安全、社会、环境、伦理与假设失效。
质询主持人证据充分性、逻辑一致性、矛盾识别和重新评估。

1.1 AgentRole 契约

AgentRole {
  id, name, role, goal, perspective,
  evaluationCriteria: string[],
  evidenceRequired: string[],
  conflictPreference: string[],
  lenses: string[],
  promptVersionId
}

1.2 确定性组件

组件职责为什么不由 LLM 主导
Planner选择角色、生成任务、建立执行顺序保证同输入同顺序和可测试性
Conflict Detector比较立场、证据、版本和置信度规则可审计，避免模型随意制造冲突
Report Generator汇总已校验对象和人工裁决报告只描述已发生的事实

1.3 角色约束

  • 初始分析阶段不得读取其他 Agent 的 Claim，避免角色相互污染。
  • 质询者不得质询自己创建的 Claim。
  • 主持人只能验证回应是否符合协议，不能擅自修改他方立场。
  • 每个断言必须标记类型、立场、重要度、置信度和证据引用。
  • 任务生成与角色分配由代码执行，LLM 只输出受 Schema 约束的内容。
设计选择： 一级角色保持五个，内部 Lens 可以多视角展开。这样既保留数据分析、运营和伦理等细分能力，又避免 Decision Map 被十多个角色切碎，降低演示成本和评审理解成本。
02 · DECISION MODEL

核心对象：Claim 与 Evidence

2.1 Claim：可质询的原子断言

Claim {
  id: UUIDv7, sessionId, agentRunId, roleId, lens,
  statement,
  type: fact | assumption | prediction | recommendation,
  stance: support | oppose | neutral,
  importance: 1..5, confidence: 0..1,
  evidenceIds: string[],
  status: proposed | supported | contested | accepted | rejected,
  rootClaimId, revisionOfClaimId?, revision,
  relations: Array<{ targetClaimId, type }>,
  respondsToChallengeId?, disposition?
}
约束实现含义
UUIDv7全球唯一，同时具有时间排序特征；非 UUIDv7 会被 Schema 拒绝。
不可原地覆盖实质修改创建新 Claim，通过 rootClaimId、revisionOfClaimId、revision 追踪版本。
关系有类型supports、contradicts、qualifies、depends_on，避免无类型 ID 数组。
接受门槛重要 Claim 进入 accepted 前必须满足证据和高严重度质询约束。

2.2 Evidence：可核验的支撑或反证

Evidence {
  id, sessionId, claimId,
  kind: project_input | calculation | external_reference | assumption,
  title, content, description, sourceRef?,
  direction: supports | opposes,
  reliability: 0..1,
  verificationStatus: unverified | verified | rejected,
  validityPeriod?: { from?, to? },
  retrievedAt, createdBy, agentRunId?
}

证据规则

  • external_reference 必须有 sourceRef。
  • assumption 不得伪装为 verified。
  • 超出 validityPeriod 的证据不能支撑最终接受。
  • 输入中的数字要记录计算口径或来源。

为什么需要这些字段

  • description 让引用型证据可读。
  • validityPeriod 处理市场、法规和价格时效。
  • reliability 与 verificationStatus 分离，避免把“像真的”当作“已核验”。
02 · DECISION MODEL

核心对象：Challenge 与 Conflict

3.1 Challenge：一次定向质疑

Challenge {
  id, sessionId, targetClaimId,
  challengerRunId, challengerRoleId,
  type: evidence_gap | logic_flaw | contradiction | feasibility | priority,
  question,
  context: { triggerClaimIds: string[], explanation },
  requiredEvidence: string[],
  severity: 1..5,
  resolutionStrategy:
    provide_evidence | revise_claim | withdraw_claim | human_decision,
  status: open | answered | validating | resolved | unresolved,
  responseClaimId?, correlationId
}

3.2 Conflict：系统检测出的结构化分歧

Conflict {
  id, sessionId, claimIds, challengeIds,
  type: evidence | logic | assumption | priority,
  summary, severity: 1..5,
  status: detected | human_review | resolved,
  humanDecisionRequired,
  resolutionSuggestion,
  impactScope: {
    analysisAreas: market | technology | finance | risk | operations[],
    stakeholders: string[]
  }
}
关键边界： resolutionSuggestion 只代表建议，不能自动关闭 Conflict。严重度 ≥ 4，或影响三个以上分析域时， 必须进入人类裁决。人工裁决前，Conflict 不得直接进入 resolved。

03 · CROSS EXAMINATION

Cross Examination 协议

3.1 执行顺序

Step 1五个角色独立分析，禁止互相读取 Claim。
Step 2通过 Schema 校验、去重，并选最多 5 个高优先级 Claim。
Step 3为每个 Claim 分配 1 至 2 个异角色质询者。
Step 4质询者生成带上下文、证据要求、严重度和解决策略的 Challenge。
Step 5目标 Agent 创建新版 Claim 回应，不覆盖原 Claim。
Step 6主持人核验回应，标记 resolved 或 unresolved。
Step 7冲突检测器生成 Conflict，高严重度冲突进入 Human Checkpoint。

3.2 七条刚性规则

  1. 初次分析期间，Agent 不得读取他方输出。
  2. 一个 Challenge 只能指向一个 Claim。
  3. 质询者不得质询自己的 Claim。
  4. Challenge 必须包含问题、上下文、证据要求、严重度和策略。
  1. 回应必须产生新版本 Claim。
  2. 主持人不能擅自修改其他 Agent 的立场。
  3. 未解决的高严重度 Conflict 不得自动关闭。

3.3 Claim 选择算法

比较顺序固定，避免结果依赖模型调用顺序或偶然排序：

importance DESC
  → evidence coverage ASC
  → confidence ASC
  → assumption > prediction > recommendation > fact
  → UUIDv7 ASC

3.4 质询者分配

角色优先质询
市场分析师市场假设、需求证据缺口、规模口径
技术专家技术可行性、依赖条件、实现周期
财务分析师成本、收入、单位经济与现金流假设
风险审查员合规、伦理和关键假设失效风险
质询主持人逻辑矛盾、跨角色冲突和证据充分性

4.2 运行限制

限制值目的
每轮目标 Claim最多 5 个控制 Demo 时长与事件规模
每个 Claim 质询者最多 2 个保留对抗，避免重复轰炸
补充质询最多 1 次防止无限循环
单次模型调用45 秒超时避免长尾请求阻塞
Repair Prompt最多 1 次修复结构错误但不无限重试

4.3 错误隔离

AgentRun 失败

记录 AGENT_RUN_FAILED，其他关键 Agent 继续运行。

Challenge 失败

只影响当前质询，不阻断其他 Challenge 分支。

结构错误

先解析、再 Schema 校验，最后执行一次 Repair Prompt。

4.4 并发与不可变性

  • 五个 Agent 使用并行执行，但每个运行单元有独立 correlationId。
  • 交给依赖的 Claim 使用 structuredClone，避免外部修改原对象。
  • CHALLENGE_CREATED 发布不可变快照，避免后续状态变化污染事件。
  • 响应 Claim 独立校验版本链、Challenge 关联和 session 归属。
  • 补充轮使用 PostgreSQL session 级 advisory lock，防止并发重复执行。
设计结果： 协议不是“让 Agent 自由辩论”，而是一个可测试、可限流、可恢复的有限状态流程。

2.2 ExecutionEvent

ExecutionEvent {
  id, sessionId, sequence, correlationId, traceId?,
  type:
    SESSION_STATE_CHANGED |
    AGENT_RUN_STARTED | AGENT_RUN_COMPLETED | AGENT_RUN_FAILED |
    CLAIM_CREATED |
    CHALLENGE_CREATED | CHALLENGE_RESOLVED | CHALLENGE_FAILED |
    CONFLICT_DETECTED | HUMAN_REVIEW_REQUIRED | SESSION_COMPLETED,
  payload, occurredAt, promptVersionId?
}

写入顺序

  1. 在同一 PostgreSQL 事务中分配 sequence。
  2. 追加不可变事件。
  3. 事务提交。
  4. 提交后才由 EventBus 发布。

SSE 恢复

  1. 客户端携带 Last-Event-ID 或 after。
  2. 先查询持久化事件进行 replay。
  3. 直播事件按 session 连续 sequence 缓冲。
  4. 重复或过期事件被幂等忽略。
一致性原则： REST 负责写入命令，SSE 负责单向事实流；任何写操作必须先完成数据库提交，之后才允许前端看到事件。

意图控制策略：从自然语言到可测试协议

1.1 上下文分层

层内容控制目的
系统约束角色、目标、评价标准、证据要求、冲突偏好、输出 Schema定义“允许生成什么”

审计上下文correlationId、promptVersionId、模型参数摘要、事件 sequence定义“结果来自哪次调用”

1.2 Prompt 设计原则

约束生成边界

  • 输出必须是结构化对象，而不是自然语言长文。
  • 枚举值、必填字段、引用关系由 Schema 决定。
  • Assumption 必须显式标记，不允许升级为 Fact。

保留人工控制

  • LLM 只能建议，不能自动关闭高风险 Conflict。
  • 人工纠偏是状态变化的一部分。
  • 补充分析最多一次，防止无限扩展。

1.3 用户需求如何被拆成协议

“让不同 Agent 互相质疑”
  → Claim 表示可质询断言
  → Challenge 表示一次定向质疑
  → 新版 Claim 表示回应
  → 主持人核验 resolved / unresolved
  → Conflict 表示未解决分歧
  → HumanDecision 表示最终裁决

1.4 模型不可控问题的工程方案

JSON parse解析失败进入明确错误路径，不把文本强行当对象。
Zod validate校验枚举、必填字段、数值范围、引用和版本关系。
Repair once只针对结构或引用问题执行一次修复 Prompt。
Isolate仍失败时记录当前 AgentRun / Challenge 失败，不毒化其他分支。

AI 协作开发方法与人工纠偏

3.1 协作角色分工

角色职责不可让渡的边界
人类负责人确定产品目标、约束范围、选择方案、最终验收高风险结论、范围扩张、真实提交

独立复审从边界、并发、安全和一致性重新检查发现的问题必须回到测试和 Commit

3.2 一轮协作的标准动作

1 · 目标用户描述业务意图与验收边界，不直接要求“写一个大而全系统”。
2 · 方案AI 给出数据结构、状态流、失败路径与测试计划。
3 · 纠偏人类接受、拒绝或收敛建议，明确不做什么。
4 · 实现按模块小步落地，每次变更对应功能与 Commit。
5 · 验证类型、单元、集成、E2E、稳定性或人工检查留下输出。
6 · 复审独立复审寻找竞态、幻觉、引用悬空和恢复问题。
7 · 记录把 Prompt、建议、纠偏、代码、测试和 Commit 写入 AI 历史。

3.3 人工纠偏的实际例子

避免角色膨胀

用户提出增加数据分析、运营、合规、伦理和逻辑分析角色。最终方案保留五个一级 Agent， 其余能力作为 Lens 内聚，避免复杂度失控。

接受独立复审

AI 初版通过了基础测试，但复审发现事件对象可变、SSE 有丢事件窗口、幂等记录可能卡死。 这些风险被逐一转化为失败测试和修复 Commit。

3.4 禁止的协作方式

  • 不允许一次性要求“把全部功能都做了”，再用单个 initial commit 伪装演进历史。
  • 不允许把用户的纠偏、失败测试或 Bug 修复从 AI 历史中删除。
  • 不允许用真实模型口吻描述 Mock fixture 结果。
  • 不允许以“AI 说通过”代替实际命令输出。

降级、恢复与失败处理

2.1 降级矩阵

故障系统行为用户可见状态
真实模型 API 不可用可切换 Mock Mode；固定 Demo 独立运行Provider 模式与 fixture 标识明确
单个 AgentRun 失败记录 AGENT_RUN_FAILED，其他角色继续失败节点与失败原因可见
单个 Challenge 失败记录 CHALLENGE_FAILED，不阻塞其他质询当前质疑标记失败或未解决
结构输出错误解析和 Schema 校验，最多一次 Repair重试中或明确失败
SSE 断线Last-Event-ID 或 after 补发事件重连后状态恢复
并发重复写Idempotency-Key + lease fencing只应用一次结果

2.2 SSE 恢复算法

Subscribe先订阅实时事件，缓存 replay 期间到达的事件。
Replay按 after / Last-Event-ID 查询持久化事件并送达。
Gap检测缺失 sequence，不丢弃后续乱序事件。
Backoffgap recovery 使用 25ms 到 1000ms 指数退避。
Idempotencesequence ≤ lastSequence 的事件被忽略。
Cleanupclose / error 时释放订阅、计时器和 heartbeat。

2.3 幂等与 lease fencing

  • 同一 Idempotency-Key 的并发请求只允许一个执行者持有 lease。
  • 进程崩溃后，过期 lease 可以被安全回收。
  • 旧 lease 不能覆盖或删除新 lease 的完成结果。
  • human decision 通过 HTTP 与 SSE 同时到达时只应用一次。

2.4 安全边界

输入与密钥

  • API 请求由 Zod 校验。
  • 项目输入作为不可信数据处理，不能覆盖系统指令。
  • API Key 只存在服务端环境变量。
  • 日志不输出密钥或完整敏感输入。

报告完整性

  • 导出前检查 Claim、Evidence 引用。
  • 检查 Conflict 是否仍处于待裁决状态。
  • 只汇总已通过 Schema 的对象。
  • 最终报告保留人工裁决与决策解释。

3.2 人工纠偏与四个真实问题

  1. replay 结束到开始订阅之间存在丢失事件窗口。
  2. replay 与实时事件合并时，低序号乱序事件在 gap 补齐前被错误丢弃。
  3. 慢速 replay 期间客户端断开，订阅和 heartbeat 可能未清理。
  4. 幂等处理中的进程崩溃可能留下永久 processing 记录。

3.3 修复路线

问题修复
事件窗口先订阅并缓存实时事件，再读取并写入 replay。
乱序expectedSequence 与 pending map，只按连续序号推进。
gap 轮询25ms 到 1000ms 指数退避，防高频 DB 查询。
连接清理replay 前注册 close / error 清理。
崩溃卡死幂等记录增加 lease token 和过期回收。
旧 lease 覆盖过期 lease 回收时使用 fencing，旧 lease 不能删除新结果。

3.4 回归测试与验证

SSE replay 期间发布的事件不丢失
2 / 3 先到的乱序事件最终按 1 / 2 / 3 输出
慢速 replay 断开后订阅和 heartbeat 被释放
gap recovery 有上限退避且无重连风暴
同 key 并发请求只执行一次
过期 lease 可以安全回收，旧 lease 无法覆盖新 lease
